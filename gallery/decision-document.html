Cloud Database Provider Selection

Acme Corp — Data Platform Team Decision Document
CANON v2.1 Author: J. Martinez Last updated: 2026-06-04 Status: In Review

§1Executive Summary

Acme Corp is building ProjectNova, a real-time analytics product requiring a new primary database. This document evaluates three cloud database providers against our constraints: sub-10ms P99 reads, less than $15K/month at launch scale, and a team of 6 engineers with primarily relational-database experience.

§1.1Background & Constraints

ProjectNova ingests event streams from customer integrations, stores dimensional data for ad-hoc querying, and serves pre-aggregated dashboards. Expected load at launch: ~2M queries/day, 500GB storage, growing 20% monthly.

Hard constraints:

  • P99 read latency < 10ms for dashboard queries
  • Monthly infrastructure cost < $15,000 at launch
  • SOC 2 Type II compliant hosting
  • Team familiarity: 6 engineers, 5 with PostgreSQL experience, 1 with DynamoDB

Soft constraints:

  • Prefer managed service to reduce operational burden
  • Schema evolution without downtime
  • Read replicas in 2+ regions within 12 months
§1.2Evaluation Methodology

Each provider was evaluated across four dimensions, weighted by team priority: Cost (25%), Performance (30%), Operations (25%), and Migration Effort (20%). Scores are 1–5; weighted totals determine the recommendation.

§2Provider Options

§2.1Provider A — CloudDB Managed PostgreSQL

Recommended
Summary: Fully managed PostgreSQL with read replicas, automated failover, and connection pooling. Closest match to existing team expertise. Predictable pricing at our projected scale.
Cost Analysis

Base instance: $2,400/mo (db.r6g.xlarge equivalent). Read replica adds $1,800/mo. Storage at 500GB: ~$575/mo. Connection pooling: included. Total: ~$4,775/mo at launch.

Scales linearly. At 5x load: ~$14,200/mo — within budget ceiling.

Performance

Benchmarked P99 read: 4.2ms on indexed queries. Write throughput: ~12K TPS sustained. Meets all latency requirements with margin. Caching layer (Redis) optional but recommended at 3x scale.

Operations

Automated backups, point-in-time recovery, automated minor-version upgrades. Major version upgrades require 15–30min maintenance window. Built-in monitoring + alerting. Team has deep PostgreSQL expertise — lowest operational learning curve.

Migration Effort

Estimated: 2–3 weeks. Existing schemas port directly. ORM compatibility is 1:1. Staging environment provisioning: 1 day. Data migration tooling (pg_dump/restore) is well-understood.

§2.2Provider B — ScaleStore Serverless NoSQL

Alternative
Summary: Serverless key-value and document store with auto-scaling and pay-per-request pricing. Excellent for unpredictable traffic but requires data model redesign. Team would need significant ramp-up time.
Cost Analysis

Pay-per-request: $1.25 per million reads, $6.25 per million writes. At 2M queries/day (70% reads, 30% writes): ~$3,100/mo. Storage: $0.25/GB/mo = $125/mo. Total: ~$3,225/mo at launch.

Caution: cost scales with traffic, not compute. At 10x load: ~$32K/mo — exceeds budget.

Performance

Single-key lookups: P99 < 5ms. Excellent for point reads. However, ad-hoc analytical queries require GSIs and may exceed 10ms for multi-dimensional filters. Dashboard queries would need pre-computation layer.

Operations

Fully serverless — zero instance management. Auto-scaling is transparent. However: no SQL, no joins, no transactions across partitions. Monitoring requires custom CloudWatch dashboards. Team has 1 engineer with experience; others need 4–6 week ramp.

Migration Effort

Estimated: 8–12 weeks. Requires full data model redesign from relational to single-table design. ORM layer must be replaced. Access patterns must be defined upfront. High risk of mid-migration rework as access patterns are discovered.

§2.3Provider C — NovaDB Distributed NewSQL

Blocked
Summary: Distributed NewSQL with PostgreSQL wire compatibility and automatic sharding. Promising technology but immature managed offering. No SOC 2 Type II certification until Q4 2026 — blocks adoption for ProjectNova launch.
Cost Analysis

Pricing not yet finalized for managed tier. Self-hosted estimates: 3-node cluster at ~$8,500/mo. Managed offering expected to be 1.5–2x self-hosted cost. Cannot produce reliable estimate.

Performance

Benchmarks show P99 reads at 6–8ms for single-region, but cross-shard queries can spike to 25ms. Write latency higher than PostgreSQL due to consensus overhead (~15ms P99). Promising for horizontal scale but unproven at our workload shape.

Operations

Managed offering in beta. Documentation gaps noted in connection handling and backup tooling. Community support only — no enterprise SLA until Q3 2026. Blocker: SOC 2 Type II certification pending, expected Q4 2026.

Migration Effort

Wire-compatible with PostgreSQL — estimated 3–5 weeks with caveats. Some PostgreSQL extensions unsupported (pg_trgm, PostGIS). Sharding key selection requires upfront analysis. Rollback story is clean due to wire compatibility.

Step 1: Audit Current State

Inventory all tables, indexes, stored procedures, and application queries against the current database. Document extension usage (pg_trgm, hstore, etc.), identify unused indexes, and catalog all connection strings across services. Produce a migration compatibility matrix.

Duration: 2–3 days   Risk: Low

Step 2: Schema Port

Generate DDL scripts for the target instance. Validate all data types, constraints, and indexes. Run schema diff tooling to confirm parity. Create reversible migration scripts using a framework the team already knows (e.g., Rails migrations, Flyway).

Duration: 3–5 days   Risk: Low

Step 3: Dual-Write

Deploy application changes that write to both old and new databases simultaneously. Validate write consistency with checksums. Monitor for latency impact on the hot path. Keep dual-write running for a minimum of one full business cycle (1 week).

Duration: 5–7 days   Risk: Medium

Step 4: Shadow Read

Route a percentage of read traffic to the new database (shadow mode — results compared but not served to users). Gradually increase from 5% to 100%. Monitor for query plan differences, latency deviations, and result mismatches.

Duration: 3–5 days   Risk: Medium

Step 5: Cutover

Flip the primary read/write path to the new database. Maintain the old database in read-only mode as a rollback target. Monitor error rates, latency percentiles, and throughput for 48 hours before declaring success.

Duration: 1 day (+ 48hr monitoring)   Risk: High

Step 6: Decommission

After 2-week bake period with no rollback triggers: remove dual-write code paths, archive old database snapshots to cold storage, update all runbooks and documentation, close the migration project.

Duration: 2–3 days   Risk: Low

§8Decision Analysis

§8.1Multi-Lens Evaluation

§8.2Dissenting Perspectives

Case for Provider B: If ProjectNova traffic proves spikier than projected (e.g., event-driven bursts), serverless auto-scaling eliminates capacity planning entirely. The cost model favors low-traffic periods. If the team invests in NoSQL expertise now, it becomes a strategic capability for future products.

Case for waiting on Provider C: NovaDB's architecture is purpose-built for the workload shape we anticipate at 12–18 month maturity. If we delay the multi-region phase to align with their SOC 2 timeline, we could adopt a system that solves our long-term sharding challenges without the operational overhead of managing it ourselves.

§8.3Recommendation

Recommendation: Provider A (CloudDB Managed PostgreSQL)

Provider A scores highest across all four evaluation dimensions. It offers the lowest risk, fastest migration, and best alignment with team capabilities. The cost model is predictable and stays within budget through 5x growth.

Conditional note: Re-evaluate Provider C at Phase 3 (Month 4) if SOC 2 certification is confirmed. Provider B remains the backup if traffic patterns prove fundamentally different from projections after 3 months of production data.
